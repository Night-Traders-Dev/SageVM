# Bolt's Performance Journal

## 2026-09-02 - Pre-Allocating Argument Names & Single-Pass Forward Stack Indexing for Function Calls
**Learning:** In the SVM interpreter (`OP_CALL` and `OP_CALL_METHOD` in `src/svm/sgvm_vm.sage`), binding function and method call arguments originally performed dynamic string concatenation (`"__arg" + str(j)`) on every call. In SageLang, string concatenation allocates dynamic C-strings (`strdup`) on the heap, causing heavy CPU and garbage collection overhead. Pre-allocating a static lookup array (`G_ARG_NAMES`) and helper (`get_arg_name`) for indices `0..15` eliminated all dynamic string allocations during argument binding. Additionally, replacing the two-pass argument collection loop (pre-filling `args` with dummy `nil` values and popping `self.stack` in reverse order) with single-pass forward stack indexing (`self.stack[base + j]`) delivered a ~9.0% real execution speedup on function call benchmarks (~1m20.15s down to ~1m12.95s over 1M iterations) and cut system/GC overhead by over 6.9s.
**Action:** Pre-allocate static string references for predictable identifier patterns (such as argument names) in interpreter call dispatches and construct argument arrays via direct forward stack indexing (`self.stack[base + j]`) instead of reverse popping.

## 2026-08-29 - O(1) Epoch-Based Global Scope Inline Cache Invalidation
**Learning:** In the SVM interpreter (`MetalVM.run` in `src/svm/sgvm_vm.sage`), invalidating the global scope inline cache during environment scope changes (`OP_PUSH_ENV`, `OP_POP_ENV`) and fallback Boundaries (`execute_op`) originally executed an O(N) loop resetting every constant pool slot (`while ci < const_len: global_cache_dict[ci] = nil`). Replacing this sequential loop with an O(1) integer epoch counter (`global_cache_epoch`) and a parallel epoch validity array (`global_cache_epoch_array`) eliminates O(N) array clearing loops across every block enter/exit and fallback opcode dispatch.
**Action:** Use integer epoch counters with parallel validity arrays for cache invalidation in virtual machine interpreters rather than looping over cache structures element-by-element.

## 2026-08-23 - Inlining OP_ARRAY, OP_TUPLE, and OP_DICT in Hot Loop & Single-Pass Stack Indexing
**Learning:** In the SVM interpreter (`MetalVM.run`), `OP_ARRAY`, `OP_TUPLE`, and `OP_DICT` opcodes were not inlined in the dispatch loop, forcing a fallback to `execute_op` on every collection literal creation. In `execute_op`, collection creation performed a two-pass algorithm: pre-populating dummy `nil` elements in a loop, then popping items off the VM stack in reverse order. Inlining `OP_ARRAY`, `OP_TUPLE`, and `OP_DICT` into `MetalVM.run` and using direct single-pass stack slicing (`stack[base + j]`) without `pop()` function calls reduced allocation benchmark runtime by ~43-47% (dropping 1M iteration execution times from ~19.1s down to ~10.1s).
**Action:** Inline collection literal creation opcodes into interpreter hot loops and construct collections via direct forward stack slot indexing (`stack[base + j]`) rather than two-pass pre-allocation and reverse popping.

## 2026-08-20 - Lazy Evaluation of Type Descriptors & Method Short-Circuiting in Index Hot Paths
**Learning:** In the SVM interpreter (`MetalVM.run`), `OP_GET_INDEX` and `OP_SET_INDEX` were unconditionally evaluating `let type_idx = type(idx)` and calling `self.is_protected(obj)` on every index operation, even when running in standard (non-safe) mode. Since `type()` allocates heap C-strings (`strdup`) and `is_protected` dispatches method calls on `self`, this caused heavy GC and function dispatch overhead. Delaying `type(idx)` evaluation inside `if safe_mode` and short-circuiting `is_protected` with `safe_mode` checks reduced system/GC overhead by over 56% (from 0.112s to 0.049s) on index-intensive loops.
**Action:** Always wrap safety checks that invoke dynamic type queries or method dispatches inside `if safe_mode` guards so default execution mode avoids unneeded heap allocations and call dispatches.

## 2026-08-17 - Stack Slot Re-use & Bypassing Push/Pop Function Calls in VM Interpreter
**Learning:** In the SVM interpreter hot loop (`MetalVM.run` in `src/svm/sgvm_vm.sage`), calling `push(stack, val)` and `pop(stack)` on every bytecode instruction introduces significant C function call dispatch and dynamic array resize overhead. Since the operand stack array retains its allocated capacity as values are pushed and popped, we can reuse existing stack slots by assigning `stack[stack_len] = val` when `stack_len < len(stack)` (falling back to `push()` only when extending capacity) and decrementing `stack_len = stack_len - 1` instead of calling `pop()`. Physical stack length is synchronized via `while len(stack) > stack_len: pop(stack)` prior to non-inlined `execute_op` fallbacks or loop termination. This optimization reduced 1M loop benchmark execution time from ~7.97s to ~7.54s (~5.4% speedup) while maintaining 100% test suite pass rate (106 tests).
**Action:** When working with interpreter operand stacks in host languages with dynamic lists, maintain a logical stack size pointer (`stack_len`), reuse existing list slots directly instead of calling `push()` / `pop()`, and synchronize the physical list length only at VM frame/fallback boundaries.

## 2026-08-20 - Bypassing dict_has Checks & Inlining Bitwise Read in Method/Property Resolution
**Learning:** In the SVM interpreter (`src/svm/sgvm_vm.sage`), method dispatch (`OP_CALL_METHOD`), function calls (`OP_CALL`), and property resolution (`OP_GET_PROPERTY`) repeatedly called `dict_has` to check for `"__methods__"`, `"__class__"`, and `"__type__"` before indexing dictionary keys. In SageLang, querying a missing key on a dictionary natively evaluates to `nil` without throwing an error. Replacing `dict_has` checks with direct dictionary key subscripting and `nil` checks bypasses multiple C-level function calls and hash search dispatches per call. Additionally, bypassing argument list allocation loops when `argc == 0` and inlining `read_be16` byte decoding in `OP_CALL_METHOD` yielded a ~13.6% speedup on 1M iteration OOP method call benchmarks (dropping runtime from ~37.87s to ~32.71s) and slashed system/GC time by over 76% (from 2.096s to 0.484s).
**Action:** Replace `dict_has` existence pre-checks with direct subscripting (`dict[key]`) and `nil` comparisons in object/method dispatch paths, and bypass argument array construction loops when `argc == 0`.

## 2026-08-16 - Fast-Pathing Primitive & Reference Equality in VM Interpreter
**Learning:** In the SVM interpreter (`MetalVM.run`), `OP_EQUAL` and `OP_NOT_EQUAL` unconditionally dispatched method calls to `self.equal_val()`. This caused `type()` to be invoked twice on every comparison (allocating C heap strings via `strdup`), incurring heavy GC and method dispatch overhead even for simple primitive comparisons (e.g., `x == 0` or `flag == false`). By testing `a == b` first as a fast-path for primitive equality and reference identity, and screening primitive non-equalities (`nil`, `boolean`, `number`) with non-allocating checks (`tonumber(v) == v`), we bypass `self.equal_val()` and `type()` calls entirely for non-collections. This yielded a ~17.3% overall speedup on equality loop benchmarks (~9.91s to ~8.19s) and cut system/GC overhead by ~89% (from 0.648s to 0.072s).
**Action:** Always fast-path direct reference/primitive equality (`a == b`) before delegating to deep-equality helpers in interpreter hot loops, and short-circuit primitive type mismatches without invoking heap-allocating dynamic type descriptors.

## 2026-08-07 - Non-Allocating Fast-Path for Numerical Arithmetic and Comparison Opcodes
**Learning:** In the SVM interpreter hot loop, calling `type(val)` on every execution of binary and comparison opcodes (e.g., `OP_ADD`, `OP_SUB`, `OP_MUL`, `OP_LESS`, etc.) causes severe performance degradation. This is because SageLang's native `type` builtin allocates heap string descriptors (such as "number") using `strdup` on each invocation, causing high CPU allocation and garbage collection overhead in hot loops. By introducing a non-allocating numeric check `val != nil and tonumber(val) == val` as a fast-path, we can identify numeric operands with zero heap allocations, yielding a ~22% real-time execution speedup on loop heavy benchmarks while maintaining 100% correct type fallbacks.
**Action:** Implement non-allocating type-checks (e.g. `tonumber(v) == v`) for high-frequency operations in interpreter loops to avoid heap string allocations and subsequent GC overhead.

## 2026-08-04 - Pre-empting Global Variable Writes & Eliminating Redundant Control Flow Safety Checks
**Learning:** In the SVM interpreter hot loop, `OP_SET_GLOBAL` originally executed constant pool bounds checking and stack peeking on every single execution, even when the inline scope resolution cache was hit. By relocating the cache check to the very top of `OP_SET_GLOBAL` (making it symmetric with `OP_GET_GLOBAL`), we completely bypass these redundant overheads. Additionally, the control flow instruction `OP_JUMP` performed a stack depth check on every jump. Since jump instructions do not modify the operand stack, checking stack safety on every jump is entirely unnecessary; loop-back boundaries and function calls already cover stack bounds checks. Eliminating this redundant check further slashes loop header overhead, decreasing loop benchmark execution times down to ~8.8s (a ~3-10% speedup on top of prior optimizations).
**Action:** Ensure cache hits are checked at the absolute beginning of dispatch blocks before any bounds checking or peek operations, and eliminate safety boundary checks from control flow instructions that do not mutate the safety resource.

## 2026-08-03 - Bypassing Stack Pre-Growing Loops in Local Writes & Caching Global Constants
**Learning:** In the SVM interpreter hot loop, local variable assignment (`OP_SET_LOCAL`) was repeatedly iterating to pre-grow the stack via a `while` loop, checking limits and executing stack push operations. Since locals are almost always written to pre-existing stack positions, bypassing the allocation loop using a fast-path branch (`if target_idx < stack_len`) completely eliminates this loop overhead. Furthermore, relocating the inline global lookup cache hit check to the top of `OP_GET_GLOBAL` bypasses unnecessary constant pool bounds checking and safe-mode prefix checks. Together, these optimizations yielded a massive ~15% speedup on the 1M iteration loop benchmark, dropping execution time from ~10.4s to ~8.9s.
**Action:** Implement fast-path branching to bypass safety loops (such as stack growth or bounds checks) when target indices are within bounds, and place inline cache checks at the absolute top of VM dispatch operations to bypass any redundant preprocessing.

## 2026-07-28 - Inline Global Variable Resolution Cache

It is crucial to clear/reset this cache on `OP_PUSH_ENV`, `OP_POP_ENV`, and fallback `execute_op` boundaries to ensure correctness when scope contexts change.
**Action:** Implement constant-index-mapped inline caches for high-frequency dynamic name resolutions in virtual machine interpreters, ensuring cache flushes at any boundary that mutates the scoping stack.

## 2026-07-16 - Hot-Loop Stack Overflow Check Optimization
**Learning:** Checking stack overflow limits (`len(stack) > max_stack`) on every single bytecode instruction inside an interpreter hot loop incurs a heavy performance penalty due to frequent list length and comparison operations. Since infinite stack growth is theoretically impossible without control-flow/loops (`OP_JUMP`, `OP_LOOP_BACK`), function/method recursion (`OP_CALL`, `OP_CALL_METHOD`), or exception handling blocks (`OP_SETUP_TRY`), restricting the overflow check to only these key opcodes preserves complete safety boundaries while eliminating the check from standard linear instructions. Removing it from conditional forward jumps (`OP_JUMP_IF_FALSE`) further optimizes loop headers, resulting in a ~41% overall execution speedup.
**Action:** Relocate resource exhaustion and safety boundary checks from the main instruction dispatch loop to control flow, function calls, and loop-back boundaries.
